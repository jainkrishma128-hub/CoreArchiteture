# 🚀 Azure Deployment & Troubleshooting Guide: CommonArchitecture

This guide provides a step-by-step breakdown of how we deployed the **CommonArchitecture** ecosystem (API + Web) to Azure, resolved HTTP 500 errors, and synchronized the database schema.

---

## 1. Initial Azure Setup (Best Practices)

### A. Environment Variables (App Settings)
In the Azure Portal, under **App Service -> Environment variables**, use the **Double Underscore (`__`)** format for nested settings.
*   **Correct Name:** `ApiSettings__BaseUrl`
*   **Incorrect Name:** `ApiSettings_BaseUrl` or `ApiSettings:BaseUrl`
*   **JWT Secret:** `Jwt__SecretKey` must be added to **both** the API and Web apps.

### B. Connection Strings
Database strings should **NOT** be in "App Settings".
*   Add them under the **Connection strings** tab.
*   **Name:** `DefaultConnection`
*   **Type:** Select **SQLAzure**.
*   **Benefit:** This allows Azure to securely inject the string and handle retries/firewalls.

## 2. Infrastructure & Code Readiness

### A. Auto-Migration & Seeding
To avoid manual SQL execution, we modified `Program.cs` in the API project:
1.  Registered `services.AddScoped<DbSeeder>();`.
2.  Added a startup block to call `await seeder.SeedAsync();`.
*This ensures that as soon as the API starts in Azure, it builds the database automatically.*

### B. The "Master Sync" Migration
When `Invalid object name` or `Invalid column name` errors occur in production:
1.  We created a unique migration: `SynchronizeDatabaseSchema.cs`.
2.  This file uses **`IF NOT EXISTS`** SQL logic to check for missing tables (`RefreshTokens`, `Menus`) and missing columns (`UpdatedAt`).
3.  It consolidates **Schema + Seed Data** into a single file for a "One-Click" setup.

## 3. Deployment Troubleshooting (Fixing HTTP 500.30)

If your app fails to start on Azure (HTTP 500.30), follow this checklist:

### Step 1: Clean Publish
In Visual Studio's Publish screen:
1.  Click the **Pencil icon** (Edit) next to Settings.
2.  Expand **File Publish Options**.
3.  Check **""Remove additional files at destination""**.
*This prevents old/corrupted DLLs from crashing the new deployment.*

### Step 2: Runtime Configuration (For Free Tier)
Azure Free Tier (F1) is 32-bit. If "Framework-dependent" fails:
1.  Change **Deployment Mode** to **Self-contained**.
2.  Change **Target Runtime** to **win-x86**.
*This uploads the .NET runtime with your app, making it more stable.*

### Step 3: Check the API URL first
Always test the API before the Web app.
*   Visit: `https://your-api.azurewebsites.net/weatherforecast`
*   If this works, your database and API are healthy.

## 4. Post-Deployment Tools

### Scalar API Documentation
We enabled Scalar in **Production** so you can test endpoints directly in the cloud.
*   **URL:** `https://your-api.azurewebsites.net/scalar/v1`
*   Use this to verify that your Auth, Products, and Menus controllers are responding correctly.

### Diagnostic Tools
In the Azure Portal, use **Diagnose and solve problems -> Application Logs**.
*   Look for **""Invalid object name""** (Missing table)
*   Look for **""Invalid column name""** (Missing migration)
*   Look for **""Login failed for user""** (Wrong connection string)

## 💡 Summary of Key Fixes
1.  **Underscores:** Switched from `_` to `__` in Azure Settings.
2.  **Missing Tables:** Created a master sync migration to create `RefreshTokens` and `Menus`.
3.  **Missing Columns:** Added `UpdatedAt` and `CategoryId` to existing tables via SQL scripts in migrations.
4.  **Base URL:** Updated the Web app's `ApiSettings:BaseUrl` to point to the live `anant-api-v2` URL.
